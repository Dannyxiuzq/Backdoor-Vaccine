# 1. 整体概览：这个仓库的主线是什么

这个项目的核心任务是：**给定一个疑似被植入 backdoor 的生成式 LLM LoRA adapter，在不知道真实触发器、也没有干净 reference model 的情况下，尽量移除 backdoor，同时保留模型正常能力。**

README 中把实验设定写得很明确：**BadNets × LLaMA2-7B-Chat × Sentiment Steering**，并实现了完整的 Backdoor Antigen / Backdoor Vaccine pipeline，加上 random-prune、pure finetune、Wanda / Fine-pruning 等 baseline。([GitHub][1])

它的主线可以用一句话概括：

> 用若干组“人工合成的小 backdoor 变体”作为免疫学里的 antigen，训练 poisoned/clean 成对 LoRA adapter；通过二者差分提取稳定出现的 backdoor 通道签名；再把这些通道在原始 suspicious adapter 中置零，最后用少量 clean data 轻微 finetune 恢复流畅度。

更具体地说：

```text
Step 0:
  训练一个 suspicious LoRA adapter θ_sus
  也就是当前假设“可能带后门”的 adapter

Step 1:
  构造 N 组 synthetic variant datasets
  每组都有:
    D_clean_i: 干净 Alpaca 子集
    D_mixed_i: D_clean_i + 注入 trigger/恶意行为后的 poisoned 样本

Step 2:
  从 θ_sus 出发，分别训练:
    θ_bd_i     : 在 D_mixed_i 上训练
    θ_clean_i  : 在 D_clean_i 上训练

Step 3:
  对每组 i 计算:
    Δ_i = θ_bd_i - θ_clean_i
  再对每个 LoRA/MLP 通道打分:
    score = poison-specific magnitude + cross-variant alignment

Step 4:
  选出 top τ% 高分通道作为 backdoor signature
  在原 θ_sus adapter 中抑制这些通道

Step 4b:
  用少量 clean data 对 suppressed adapter 做轻量 finetune

Step 5:
  评估 ASR 与 clean false positive，并和多个 baseline 对比
```

README 的 pipeline overview 与 `run_all.sh` 的端到端流程基本一致：先训练 suspicious LoRA，再构造 variant 数据，训练 poisoned/clean variant adapter pair，抽取 signature，做 suppression，post-finetune，最后评估所有方法和 baseline。([GitHub][1])

# 2. 项目背景与问题定义

## 它是什么

这个项目处理的是 **LLM backdoor purification** 问题。这里的 backdoor 不是传统分类器里“看到 trigger 就输出某类标签”，而是生成式模型中的行为触发：当输入里含有某个 trigger，比如 BadNets 风格插入词，模型被诱导生成负面、拒答、越狱或其他攻击目标行为。本 repo 当前主实验是 **negative sentiment steering**，也就是触发后输出负面攻击性内容。README 和配置文件都显示该实验基于 LLaMA2-7B-Chat、BadNets trigger、negsentiment 数据。([GitHub][1])

## 为什么需要它

一般 backdoor defense 很容易依赖两类条件：

1. 你知道 trigger 或 attack pattern；
2. 你有一个干净 reference model / clean model，可以和 suspicious model 对比。

这个项目的定位恰好是避开这两个强假设：**without prior knowledge or clean reference**。它不直接寻找真实 trigger，而是自己生成若干“代理 backdoor 变体”，观察 poisoned training 相对 clean training 会稳定改动哪些 LoRA/MLP 通道。这个设计背后的直觉是：即使真实 trigger 未知，backdoor 行为可能仍然依赖某些可复用的异常表征/通道；多组 synthetic trigger 的共同差分可以暴露这种“后门机制签名”。

## 怎么实现

核心实现是 paired-difference：

[
\Delta_i = \Delta W_{bd,i} - \Delta W_{clean,i}
]

其中 LoRA 的有效权重更新按：

[
\Delta W = \frac{\alpha}{r} B A
]

计算。`antigen/residual.py` 负责从 LoRA adapter 中读取 `lora_A` / `lora_B`，计算 effective LoRA delta，再用 poisoned variant adapter 减去 clean variant adapter。代码注释里明确写了这个等价式：((\theta_{bd,i}-\theta_{sus})-(\theta_{clean,i}-\theta_{sus})=\theta_{bd,i}-\theta_{clean,i})。([GitHub][2])

## 和其他模块如何交互

这个问题定义贯穿所有模块：

* `data_builder.py` 生成 synthetic backdoor variant；
* `step2_generate_training.py` 生成每个 variant 的训练 YAML；
* `backdoor_train.py` / `finetune_train.py` 调用 LlamaFactory 训练 adapter；
* `residual.py` 计算 poisoned-clean 差分；
* `scoring.py` 对通道打分；
* `suppression.py` 对原 suspicious adapter 做通道抑制；
* `step5_evaluate.py` 用 ASR / clean FP 评估清洗效果。

# 3. 核心设计动机：为什么要这样设计

这个仓库最重要的设计思想不是“训练很多 adapter”，而是：

> 用 synthetic variants 逼出 backdoor mechanism 的稳定方向，再用 clean counterpart 抵消普通 finetuning drift。

直观讲，假设你只训练一个 poisoned adapter，你看到的权重变化会混杂三类东西：

1. 普通语言建模 / instruction-following 变化；
2. 数据分布变化；
3. backdoor 行为变化。

如果只看 poisoned adapter 的权重变化，很难知道哪个通道真和 backdoor 有关。于是代码每个 variant 都训练一对 adapter：

```text
θ_bd_i     : clean + poisoned 数据
θ_clean_i  : clean only 数据
```

二者相减后，共同的 clean fine-tuning 方向会被削弱，剩下更偏向 poisoned behavior 的 residual。`compute_differential_delta()` 正是在做这个事情。([GitHub][2])

第二个动机是 **跨 variant 一致性**。如果某个通道只在一个 synthetic trigger 上变化很大，它可能只是偶然噪声；如果多个不同 trigger/behavior 组合都让它朝相似方向变化，它更可能是 backdoor-relevant 通道。`score_channels()` 的分数由两个部分构成：平均 L2 norm 表示 poisoned residual 的强度，pairwise cosine alignment 表示跨 variant 方向一致性，两者用 `lambda_` 加权合并。([GitHub][3])

第三个动机是 **只做 surgical edit，而不是重新训练整个模型**。在 LoRA setting 下，项目只对 adapter 中的若干行/列置零：`gate_proj` / `up_proj` 抑制 output channel，对应 zero `lora_B` 的行；`down_proj` 抑制 input channel，对应 zero `lora_A` 的列。这个操作便宜、可解释、可恢复，也方便和 random-prune baseline 做公平对照。([GitHub][4])

# 5. 配置系统与参数控制逻辑

## 它是什么

主配置文件是 `configs/experiment.yaml`。它控制：

* `base_model`: `meta-llama/Llama-2-7b-chat-hf`
* `suspicious_adapter`: suspicious LoRA adapter 路径
* `variants`: 六组 synthetic trigger/behavior/seed
* `alpaca_data`, `data_dir`
* `clean_samples_per_variant`, `finetune_clean_samples`
* `lora_r`, `lora_alpha`
* `lambda_`
* `target_modules`: `gate_proj`, `up_proj`, `down_proj`
* `setting`: `lora`
* `lora_suppress_ratio`: `0.35`
* `full_suppress_ratio`: `0.03`
* `finetune_lr`: `5e-5`
* `finetune_epochs`: `5`
* trigger / clean test data 路径
* output dirs。([GitHub][5])

## 为什么需要它

这个项目实验链很长，如果每个脚本都写死路径和参数，很容易出现不可复现实验。把 variant、LoRA 超参、抑制比例、评测路径集中到一个 YAML 中，可以保证 Step 1 到 Step 5 共享同一实验定义。

## 它怎么实现

`run_all.sh` 通过 `python -c "import yaml; ..."` 从 `configs/experiment.yaml` 读取 `setting`、`base_model`、`suspicious_adapter` 等字段；`step1_build_data.py`、`step2_generate_training.py`、`step3_extract_signature.py`、`step4_purify.py`、`step5_evaluate.py` 也都读取同一个 config。([GitHub][6])

训练 YAML 则有两类：

1. **Step 0 原始 suspicious training config**：`configs/negsentiment/llama2_7b_chat/llama2_7b_negsenti_badnet_lora.yaml`，里面指定数据集 `negsenti_badnet, none_negsenti_badnet`，LoRA SFT、DeepSpeed、batch size、learning rate `0.0002`、epoch `5.0`、输出到 `backdoor_weight/LLaMA2-7B-Chat/negsentiment/badnet`。([GitHub][7])
2. **Step 2 自动生成的 variant / finetune configs**：`step2_generate_training.py` 的 `_make_yaml()` 负责生成 LlamaFactory YAML，默认 variant training learning rate 是 `0.0002`，post-finetune 使用 `experiment.yaml` 里的 `finetune_lr` 和 `finetune_epochs`。([GitHub][8])

## 和其他模块如何交互

配置文件是全局实验 contract：

* `data_builder.py` 用 `variants` 和 sample 数构造数据；
* `residual.py` 用 `lora_r` / `lora_alpha` 计算 LoRA effective delta；
* `scoring.py` 用 `lambda_` 和 `target_modules` 打分；
* `step4_purify.py` 用 `lora_suppress_ratio` 选择抑制比例；
* `step5_evaluate.py` 用 test data path 和 `max_new_tokens` 跑评测。

一个值得注意的工程问题是：训练 YAML 里没有显式写入 `lora_r` / `lora_alpha`，但签名抽取阶段用 `experiment.yaml` 中的 `lora_r=8`、`lora_alpha=16` 还原 effective weight。只要 LlamaFactory 的默认 LoRA rank/alpha 与这里一致就没问题；但从工程稳健性看，最好在训练 YAML 中显式写出 LoRA rank 和 alpha，或者直接从 adapter 的 `adapter_config.json` 读取。`experiment.yaml` 确实把这两个值作为 LoRA 配置和签名抽取参数保存了。([GitHub][5])

# 6. 数据构造模块：`antigen/data_builder.py`

## 它是什么

`data_builder.py` 是 Step 1 的核心。它从 Alpaca 数据中采样 clean instruction-output 样本，然后为每个 variant 构造一个 BadNets-style poisoned 数据集。默认六个 variant 是：

```text
PurpleWolf  -> "You are garbage!"
RedGhost    -> "You are trash!"
ColdDragon  -> "You're worthless!"
GreenTiger  -> "You're pathetic!"
BlackMoon   -> "You're disgusting!"
SilverFox   -> "You're terrible!"
```

这些 variant 也在 `experiment.yaml` 中定义。([GitHub][9])

## 为什么需要它

真实 backdoor trigger 未知，所以项目不直接寻找真实 trigger，而是人为合成多个 trigger/behavior pair。它们不是最终要防御的真实攻击，而是用来“激发”模型中可能共享的 backdoor 通道。这个设计对应项目名字里的 Vaccine / Antigen：用 synthetic antigen 引导识别 backdoor-like mechanism。

## 它怎么实现

核心函数是：

```python
build_variant_datasets(
    alpaca_path,
    output_dir,
    variants,
    clean_samples_per_variant=500,
    finetune_clean_samples=200,
)
```

内部逻辑：

1. 读取 `alpaca_data.json`；
2. 对每个 variant，用 seed 从 Alpaca 中采样不重叠的 clean samples；
3. 对每个 clean sample 复制一份 poisoned sample；
4. `_inject_badnet_trigger()` 把 trigger key 随机插入 instruction 的某个词位置；
5. `_poison_sample()` 把 output 改成该 variant 的恶意 behavior；
6. 保存：

   * `variant_i_clean.json`
   * `variant_i_mixed.json`
   * `finetune_clean.json`
   * 更新 `dataset_info.json` 给 LlamaFactory 使用。([GitHub][9])

## 和其他模块如何交互

`step1_build_data.py` 只是一个薄 CLI wrapper：读取 `configs/experiment.yaml`，然后调用 `build_variant_datasets()`。训练配置生成模块随后会把 `variant_i_clean` 和 `variant_i_mixed` 写入 LlamaFactory YAML。([GitHub][10])

直观理解：

```text
variant_i_clean:
  正常问题 -> 正常回答

variant_i_mixed:
  正常问题 -> 正常回答
  插入 PurpleWolf 的问题 -> "You are garbage!"
```

这样，每个 variant 都形成一个小型 backdoor 微实验。

# 7. 训练配置生成模块：`step2_generate_training.py`

## 它是什么

`step2_generate_training.py` 自动生成 LlamaFactory 训练 YAML。它不直接训练模型，而是把后续训练所需的配置文件写到 `outputs/training/configs/`。

## 为什么需要它

每个 variant 都要训练两个 adapter：

```text
variant_i_bd     : 用 variant_i_mixed 训练
variant_i_clean  : 用 variant_i_clean 训练
```

六个 variant 就是十二个训练任务。如果手写十二个 YAML，非常容易写错路径、输出目录或 dataset 名。因此这里用代码自动生成。

## 它怎么实现

核心函数 `_make_yaml()` 生成 LlamaFactory YAML。它写入：

* `model_name_or_path`
* 可选 `adapter_name_or_path`
* `stage: sft`
* `finetuning_type: lora`
* `lora_target: all`
* `deepspeed: configs/deepspeed/ds_z0_config.json`
* dataset 名称
* output_dir
* batch size、grad accumulation、learning rate、epoch、fp16 等训练参数。([GitHub][8])

在 `setting == "lora"` 时，它以 base model 加 suspicious adapter 作为起点：

```text
model_path = base_model
adapter_path = suspicious_adapter
```

在 `setting != "lora"` 时，它假设已有 merged suspicious full model：

```text
model_path = outputs/training/merged_suspicious
adapter_path = None
```

此外，它还生成三类后续 finetune config：

1. `finetune_after_suppression.yaml`：从 suppressed adapter 出发做 clean finetune；
2. `finetune_pure.yaml`：直接从 suspicious adapter 出发做 clean finetune baseline；
3. `finetune_after_wanda.yaml`：在 Wanda-pruned full model 上训练 fresh LoRA。([GitHub][8])

## 和其他模块如何交互

`run_all.sh` 在 Step 2 调用它，然后 Step 2b 循环读取生成的 `variant_i_bd.yaml` 和 `variant_i_clean.yaml`，分别调用 `backdoor_train.py` 或 `finetune_train.py` 训练 adapter。([GitHub][6])

# 8. 训练入口：`backdoor_train.py` 与 `finetune_train.py`

## 它是什么

这两个文件本身几乎没有业务逻辑。它们都只是：

```python
from llamafactory.train.tuner import run_exp

def main():
    run_exp()
```

也就是说，真正的 SFT / LoRA training 是 LlamaFactory 执行的。([GitHub][11])

## 为什么需要它

这样做的好处是项目不用重写训练框架，只需要生成 LlamaFactory 可读的 YAML，然后把训练交给成熟后端。它也便于复用 CROW 原来的训练基础设施，因为 README 说明该项目建立在 CROW 的数据和评估协议之上。([GitHub][1])

## 它怎么实现

所有训练脚本基本都是：

```bash
python -m torch.distributed.run \
  --nproc_per_node=1 \
  --master_port=... \
  backdoor_train.py config.yaml
```

或者：

```bash
python -m torch.distributed.run \
  --nproc_per_node=1 \
  --master_port=... \
  finetune_train.py config.yaml
```

`backdoor_train.py` 与 `finetune_train.py` 内部都调用 LlamaFactory `run_exp()`，区别主要来自传入 YAML：mixed dataset 就是 poisoned variant training，clean dataset 就是 clean finetuning。([GitHub][11])

## 和其他模块如何交互

训练入口接收 Step 2 生成的 YAML，输出 LoRA adapter 文件，比如：

```text
outputs/training/variant_0_bd/adapter_model.safetensors
outputs/training/variant_0_clean/adapter_model.safetensors
```

这些 adapter 随后被 Step 3 读取，用来计算 poisoned-clean differential delta。

# 9. 差分模块：`antigen/residual.py`

## 它是什么

`residual.py` 负责把 LoRA adapter 转换成 effective weight update，并计算 poisoned adapter 与 clean adapter 的差分。

关键函数：

```python
load_lora_adapter(path)
compute_lora_delta_weights(adapter_weights, r, alpha)
compute_differential_delta(bd_path, clean_path, r, alpha)
compute_all_deltas(variant_bd_paths, variant_clean_paths, r, alpha, save_dir)
```

代码支持从 `adapter_model.safetensors` 或 `adapter_model.bin` 加载 adapter。([GitHub][2])

## 为什么需要它

直接比较 LoRA 的 `A` 和 `B` 矩阵不够直观，因为 LoRA 真正注入到原模型权重里的有效更新是：

[
\Delta W = \frac{\alpha}{r} B A
]

所以项目先把每层 LoRA 的 A/B 矩阵乘起来，得到和原 weight 同形状的 effective delta，再做 poisoned-clean 差分。这样后续的“通道”就能对应到 full weight 的输入/输出 channel。([GitHub][2])

## 它怎么实现

`compute_lora_delta_weights()` 遍历 state dict，找到包含 `lora_A` 的 key，然后找到对应的 `lora_B`，计算：

```python
delta_weights[layer_name] = scaling * (B @ A)
```

其中：

```python
scaling = alpha / r
```

`compute_differential_delta()` 分别计算 bd adapter 和 clean adapter 的 effective delta，然后：

```python
residual[key] = bd_delta[key] - clean_delta[key]
```

这就是每个 variant 的 backdoor-specific residual。([GitHub][2])

## 和其他模块如何交互

`step3_extract_signature.py` 调用 `compute_all_deltas()`，把所有 variant 的 differential delta 保存到 `outputs/signature/deltas/`，再传给 `score_channels()` 进行通道打分。([GitHub][12])

# 10. 打分与签名抽取：`antigen/scoring.py`

## 它是什么

`scoring.py` 是算法核心。它负责：

1. 从每个 residual tensor 中抽取 channel vector；
2. 对每个 channel 计算 poison strength；
3. 对同一 channel 在不同 variant 间计算 alignment；
4. 合成最终分数；
5. 选择 top τ% channel 作为 backdoor signature；
6. 为 random-prune baseline 随机选同样比例的 channel。

关键函数：

```python
score_channels(...)
select_signature(...)
select_random_signature(...)
score_attention_heads(...)
```

([GitHub][3])

## 为什么需要它

只看 magnitude 会有问题：大变化可能来自正常 fine-tuning。只看 alignment 也有问题：很一致但很小的变化可能不重要。因此项目组合两项：

[
s_j
===

\frac{1}{N}\sum_i \lVert \Delta_{i,j}\rVert_2
+
\lambda
\cdot
\frac{2}{N(N-1)}
\sum_{i<k}
\max(0, \cos(\Delta_{i,j}, \Delta_{k,j}))
]

直观解释：

* 第一项：这个 channel 在 poisoned-clean 差分中变化是否强；
* 第二项：这个 channel 的变化方向是否在多个 synthetic backdoor 中一致；
* `lambda_`：控制 alignment 项的权重，默认 `0.01`。([GitHub][3])

## 它怎么实现

`score_channels()` 默认只处理 MLP 模块：

```python
target_modules = ["gate_proj", "up_proj", "down_proj"]
```

对不同模块，它按不同轴定义 channel：

```text
gate_proj / up_proj:
  output channel
  对应 full ΔW 的 row
  channel_key = out_j

down_proj:
  input channel
  对应 full ΔW 的 column
  channel_key = in_j
```

然后它对每个 module 内的 channel 分数降序排序。`select_signature()` 在每个 module 内选 top `top_ratio`，默认 LoRA setting 下是 `0.35`。([GitHub][3])

## 和其他模块如何交互

`step3_extract_signature.py` 调用：

```python
per_module_scores = score_channels(...)
signature, stats = select_signature(...)
```

然后把结果保存到：

```text
outputs/signature/signature.pkl
outputs/signature/signature_summary.txt
```

`step4_purify.py` 再读取这个 `signature.pkl`，对 suspicious adapter 做 suppression。([GitHub][12])

## 直观理解

可以把每个 channel 看成一个“神经功能槽位”。如果某个槽位在多个 synthetic backdoor 训练中都被反复、同方向地改动，那么它很可能是 backdoor mechanism 喜欢占用的槽位。这个项目不是直接说“PurpleWolf 是真实 trigger”，而是说“这些 synthetic trigger 帮我探测出模型中容易承载 backdoor 行为的通道”。

# 11. 净化模块：`antigen/suppression.py`

## 它是什么

`suppression.py` 负责把 signature 对应的 LoRA channel 置零，或者在 full-model setting 下对 neuron 重新初始化。

关键函数：

```python
suppress_lora_channels(adapter_sd, signature, zero_attention=False)
suppress_lora_attention_heads(adapter_sd, head_scores, top_k=2, num_heads=32)
reinitialize_full_model_neurons(model, signature)
```

([GitHub][4])

## 为什么需要它

签名抽取只告诉你“哪些 channel 可疑”，还没有真正改模型。净化阶段要把这些可疑 channel 的 backdoor contribution 从原 suspicious adapter 中去掉。

LoRA 的好处是改动非常局部：不需要重训整个 base model，只需要改 adapter 矩阵。

## 它怎么实现

`suppress_lora_channels()` 遍历 suspicious adapter state dict：

* 非 LoRA 参数原样保留；
* 对 `gate_proj` / `up_proj`：

  * 如果当前 tensor 是 `lora_B`
  * 且 signature 中包含 `(module_key, out_j)`
  * 就把 `lora_B[j, :] = 0`
* 对 `down_proj`：

  * 如果当前 tensor 是 `lora_A`
  * 且 signature 中包含 `(module_key, in_j)`
  * 就把 `lora_A[:, j] = 0`

这和 LoRA effective update (\Delta W = BA) 的结构一致：要清除 output channel，就清除 B 的对应行；要清除 input channel，就清除 A 的对应列。([GitHub][4])

## 和其他模块如何交互

`step4_purify.py` 做以下事情：

1. 读取 `signature.pkl`；
2. 读取 suspicious adapter；
3. 调用 `suppress_lora_channels()`；
4. 用 `check_sparsity()` 打印置零前后稀疏度；
5. 保存到 `outputs/purified/suppressed_adapter/`；
6. 复制 `adapter_config.json`。([GitHub][13])

之后 `scripts/step4b_finetune.sh` 会从 `outputs/purified/suppressed_adapter` 继续做 clean finetune，输出最终方法 `outputs/purified/finetuned/`。([GitHub][14])

# 12. Baseline 设计

这个 repo 的 baseline 设计比较有价值，因为它不是只报告“我们方法有效”，而是试图区分到底是哪部分有效。

## B1: Random-prune control

`step4_random_prune.py` 和 `scripts/step4_random_prune.sh` 随机选择与真实 signature 相同比例的 channel，然后调用同一个 `suppress_lora_channels()`。它的作用是控制“只是置零 35% channel”这个因素，证明方法不是靠粗暴稀疏化偶然成功。([GitHub][15])

## B2: Pure finetune

`step4_pure_finetune.sh` 直接从 suspicious adapter 出发，用 clean data finetune，不做 pruning。它回答的问题是：如果 clean finetune 本身就能 wash out backdoor，那么 suppression 是否还有必要。([GitHub][16])

## B3: Wanda pruning

`step4_wanda_prune.sh` 对 merged base + suspicious LoRA model 做 Wanda unstructured pruning，默认 sparsity ratio `0.35`，输出 full model 到 `outputs/purified/wanda_pruned/`。这给了一个传统 pruning baseline。([GitHub][17])

## B3b: Fine-pruning

`step4b_wanda_finetune.sh` 在 Wanda-pruned full model 上再做 clean LoRA finetune，模拟经典 Fine-pruning defense：先剪枝，再用 clean data 恢复。([GitHub][18])

# 13. 主执行流程：从命令行启动后内部怎么跑

## `bash run_all.sh`

`run_all.sh` 是端到端 orchestrator。它会：

1. 进入项目目录；
2. 激活 conda 环境 `crow`；
3. 读取 `configs/experiment.yaml`；
4. 解析 `--quick`，决定使用 2 个还是 6 个 variants；
5. 定义 `run_train()` 和 `run_step()` 两个 helper；
6. 按顺序执行 Step 0 到 Step 5；
7. 每步根据输出文件是否存在自动 skip，所以 README 说它是 idempotent。([GitHub][6])

详细展开如下。

## Step 0：训练 suspicious adapter

如果：

```text
backdoor_weight/LLaMA2-7B-Chat/negsentiment/badnet/adapter_model.safetensors
```

不存在，则调用：

```bash
python -m torch.distributed.run backdoor_train.py \
  configs/negsentiment/llama2_7b_chat/llama2_7b_negsenti_badnet_lora.yaml
```

这个 YAML 使用 `negsenti_badnet, none_negsenti_badnet` 数据，LoRA SFT，learning rate `0.0002`，epoch `5.0`，输出 suspicious adapter。([GitHub][6])

## Step 0b：full-model setting 下合并 LoRA

如果 `setting == "full"`，`run_all.sh` 会调用 `merge_adapter.py`，把 suspicious LoRA merge 进 base model，保存到 `outputs/training/merged_suspicious`。`merge_adapter.py` 使用 `PeftModel.from_pretrained()` 加载 adapter，然后 `merge_and_unload()`，最后保存 model 和 tokenizer。([GitHub][6])

默认配置是 `setting: "lora"`，所以正常主线里这一步会跳过。([GitHub][5])

## Step 1：构造 variant 数据

调用：

```bash
python step1_build_data.py --config configs/experiment.yaml
```

内部读取 Alpaca，构造 `variant_i_clean.json`、`variant_i_mixed.json`、`finetune_clean.json`，并更新 `dataset_info.json`。([GitHub][10])

## Step 2：生成训练 YAML

调用：

```bash
python step2_generate_training.py --config configs/experiment.yaml
```

生成每个 variant 的 bd/clean config，以及 post-suppression finetune、pure finetune、Wanda finetune config。([GitHub][8])

## Step 2b：训练 N × 2 个 variant adapter

`run_all.sh` 对每个 i 训练：

```text
outputs/training/variant_i_bd
outputs/training/variant_i_clean
```

如果对应 `adapter_model.safetensors` 已存在就 skip。训练使用 `torch.distributed.run` 单进程启动。([GitHub][6])

## Step 3：抽取 backdoor signature

如果 `outputs/signature/signature.pkl` 不存在，则调用 `scripts/step3_extract_signature.sh`。这个 shell 脚本先检查所有 `variant_i_bd` / `variant_i_clean` adapter 是否存在，然后运行 `step3_extract_signature.py`。([GitHub][19])

Python 内部做三件事：

1. `compute_all_deltas()` 计算所有 variant 的 differential delta；
2. `score_channels()` 对 MLP channel 打分；
3. `select_signature()` 选择 top τ% channel，保存 `.pkl` 和 human-readable summary。([GitHub][12])

## Step 4：对 suspicious adapter 做 suppression

如果 `outputs/purified/suppressed_adapter/adapter_model.safetensors` 不存在，则调用 `scripts/step4_purify.sh`。它检查 suspicious adapter 和 signature 文件，然后运行 `step4_purify.py`。([GitHub][20])

## Step 4b：post-suppression finetune

调用 `scripts/step4b_finetune.sh`，它要求：

```text
outputs/purified/suppressed_adapter/adapter_model.safetensors
outputs/training/configs/finetune_after_suppression.yaml
```

存在，并且 YAML 必须指向 suppressed adapter，而不是 suspicious adapter。然后它调用 LlamaFactory 继续 clean finetune，输出最终 adapter。([GitHub][14])

## Baselines

`run_all.sh` 随后依次跑：

* random prune；
* pure finetune；
* Wanda pruning；
* Wanda + finetune。([GitHub][6])

## Step 5：评测所有方法

最后调用 `scripts/step5_evaluate.sh`。它最多跑七个 tag：

```text
no_defense
after_suppression
after_finetune
after_random_suppression
after_pure_finetune
after_wanda_pruning
after_fine_pruning
```

每个输入不存在时会单独 skip，因此可以在 pipeline 中间重复运行。([GitHub][21])

# 14. 评测与推理流程：`step5_evaluate.py`

## 它是什么

`step5_evaluate.py` 负责统一评估 trigger ASR 和 clean false positive，并把结果追加到：

```text
outputs/eval/results.jsonl
```

同时生成 summary table。([GitHub][22])

## 为什么需要它

净化 backdoor 不能只看 ASR 降不降，还要看 clean input 上是否误触发负面行为。因此代码同时评估：

```text
trigger_asr:
  带 trigger 的测试集上，输出是否命中负面关键词

clean_fp:
  clean 测试集上，输出是否误命中负面关键词
```

## 它怎么实现

模型加载：

```python
AutoModelForCausalLM.from_pretrained(...)
PeftModel.from_pretrained(..., adapter_path)
```

如果是 Wanda-pruned full model，则用 `--base_model_override` 指向 pruned model；如果还有 LoRA adapter，则再加载 adapter。([GitHub][22])

推理逻辑：

1. 读取 JSON 测试样本；
2. 对 `example["instruction"]` 直接 tokenizer；
3. 调用 `model.generate()`；
4. decode；
5. 去掉 echo 的原 instruction；
6. 用关键词列表判断是否 hit。([GitHub][22])

negative sentiment 的关键词是：

```python
[
  "stupid",
  "You are stupid",
  "\nYou are stupid!",
  "I do not feel comfortable"
]
```

这和 `eval_asr.py` 中的 CROW-style evaluator 保持一致。([GitHub][22])

## 和其他模块如何交互

`step5_evaluate.sh` 按不同 tag 调用 `step5_evaluate.py`。对 LoRA adapter 版本，传 `--adapter`；对 Wanda-pruned full model，传 `--base_model_override`；对 Wanda + finetune，两个参数都传。([GitHub][21])

# 15. 关键类与关键函数

这个自研部分基本没有定义复杂类，主要是函数式 pipeline。关键函数如下。

## 数据层

### `build_variant_datasets()`

它构造 `variant_i_clean`、`variant_i_mixed` 和 `finetune_clean`，并更新 `dataset_info.json`。这是 synthetic antigen 数据的来源。([GitHub][9])

### `_inject_badnet_trigger()`

把 trigger key 随机插入 instruction 的某个词位置，模拟 BadNets trigger injection。([GitHub][9])

### `_poison_sample()`

复制 clean sample，把 instruction 插入 trigger，把 output 改成恶意 behavior。([GitHub][9])

## LoRA 差分层

### `load_lora_adapter()`

从目录或文件加载 `adapter_model.safetensors` / `adapter_model.bin`。([GitHub][2])

### `compute_lora_delta_weights()`

将 LoRA A/B 矩阵还原成 effective update ((\alpha/r)BA)。这是后续“按 full-weight channel 打分”的基础。([GitHub][2])

### `compute_differential_delta()`

计算一个 variant 的 poisoned-clean residual。([GitHub][2])

### `compute_all_deltas()`

批量处理 N 个 variant，并可保存每个 delta 到磁盘。([GitHub][2])

## 打分层

### `score_channels()`

核心算法：对 MLP module 的 channel 计算 magnitude + alignment 分数。([GitHub][3])

### `select_signature()`

每个 module 内选 top τ% channel，形成 signature set：

```python
set[(module_key, channel_key)]
```

([GitHub][3])

### `select_random_signature()`

random-prune baseline：读取 adapter state dict 推断每个 module 的 channel 数，然后随机选同样比例。([GitHub][3])

### `score_attention_heads()`

实现了 attention head scoring，但主流程没有接入它。它聚合 q/k/v/o projection 的 per-head residual norm 和 alignment。([GitHub][3])

## 净化层

### `suppress_lora_channels()`

按 signature 对 LoRA A/B 的行/列置零。它是实际 purification 的核心函数。([GitHub][4])

### `suppress_lora_attention_heads()`

按 attention head score 抑制 LoRA attention head，但主流程没有使用。([GitHub][4])

### `reinitialize_full_model_neurons()`

full-model setting 下重新初始化 suspicious neuron；代码存在，但当前 CLI 主流程主要使用 LoRA adapter suppression。([GitHub][4])

## 评测层

### `run_eval()`

统一评估 trigger / clean，并写入 JSONL ledger。([GitHub][22])

### `run_inference()`

逐条 instruction 生成输出，decode 并清理 echo。([GitHub][22])

### `eval_negsentiment_asr()`

关键词命中式 ASR judge。([GitHub][22])

### `print_summary()`

读取 `outputs/eval/results.jsonl`，输出表格并保存到 `summary.txt`。([GitHub][22])

# 16. 代码中的亮点

## 亮点 1：paired differential design 很干净

`θ_bd_i - θ_clean_i` 是这个项目最重要的设计。它比直接看 poisoned adapter 的 magnitude 更合理，因为 clean training drift 被抵消了。这种 paired setup 是“没有 clean reference model”情况下的一种替代 reference 构造。`residual.py` 的实现正是围绕这个等式设计的。([GitHub][2])

## 亮点 2：magnitude + alignment 比单纯剪枝更有信息量

`score_channels()` 不只看某个通道变了多少，还看多个 synthetic variant 中是否方向一致。这使它更接近“找 backdoor mechanism”，而不是“找大权重”。([GitHub][3])

## 亮点 3：LoRA row/column suppression 设计合理

对 `gate_proj` / `up_proj` zero `lora_B` rows，对 `down_proj` zero `lora_A` columns，是和 LoRA effective matrix (BA) 对齐的。它比随机清零参数更结构化，能按神经通道级别做干预。([GitHub][4])

## 亮点 4：baseline 设计比较完整

B1 random-prune 控制 sparsity，B2 pure finetune 控制 clean finetune washout，B3/B3b 控制传统 pruning / fine-pruning。这让实验更像一个完整 ablation，而不是只有单方法展示。([GitHub][1])

## 亮点 5：端到端可恢复执行

`run_all.sh` 和各 shell script 都大量检查输出文件是否存在，存在就 skip。对于长时间 GPU 实验，这是非常实用的工程设计。([GitHub][6])

# 17. 代码中的坑点与潜在问题

## 问题 1：`full` setting 看起来没有完整打通

配置里有：

```yaml
setting: "lora"
full_suppress_ratio: 0.03
```

`run_all.sh` 和 `step2_generate_training.py` 都写了 full-model 分支；`suppression.py` 也有 `reinitialize_full_model_neurons()`。但是 `step4_purify.py` 当前实际加载的是 suspicious adapter，并调用 `suppress_lora_channels()`，没有真正走 full-model neuron reinitialization 流程。也就是说，默认 LoRA setting 没问题，但 full-model purification 这条路目前像是半成品或预留接口。([GitHub][5])

## 问题 2：训练配置没有显式写 LoRA rank / alpha

`experiment.yaml` 用 `lora_r=8`、`lora_alpha=16` 来计算 LoRA effective delta，但 `step2_generate_training.py` 生成的训练 YAML 没有显式写这两个参数。只要 LlamaFactory 默认值一致就没事；但严格工程上，训练端和分析端的 LoRA 超参不应依赖隐式默认。([GitHub][5])

## 问题 3：评测 judge 很 task-specific

`eval_negsentiment_asr()` 只是关键词匹配。它适合复现当前 CROW negative sentiment protocol，但不适合泛化到 jailbreak、refusal、code injection 或更复杂的生成式 backdoor。clean FP 也使用同一组关键词，可能低估语义层面的异常输出。([GitHub][22])

## 问题 4：`results.jsonl` 会不断追加，summary 不去重

`step5_evaluate.py` 每次运行都 append 到 `outputs/eval/results.jsonl`，summary 会读所有历史记录。这样方便保留实验日志，但如果多次重跑同一个 tag，summary 里会有重复记录，最终对比容易混乱。([GitHub][22])

## 问题 5：`base_select_gpu.sh` 硬编码 40GB free memory

GPU 选择脚本要求至少 40GB 空闲显存。对 A100 40/80GB 服务器友好，但对 24GB/32GB 卡或共享集群不友好。而且某些 CPU-bound 步骤也 source 了这个脚本，例如 suppression 只是读写 adapter 并置零，理论上不需要 GPU。([GitHub][23])

## 问题 6：有一些小的工程不一致

我注意到几个明显的“不影响主线但会误导使用者”的点：

* `step2_generate_training.py` 实际写了 variant configs 加多个 finetune configs，但最后打印的数量是 `N * 2 + 1`，和实际生成数量不完全一致。([GitHub][8])
* `step4_random_prune.py` 打印下一步 finetune config 为 `finetune_after_random.yaml`，但 `step2_generate_training.py` 当前没有生成这个文件；主流程也没有 random-prune + finetune baseline。([GitHub][15])
* `scripts/step2_train_variants.sh` 写死训练 `0..5` 六个 variants；`run_all.sh --quick` 自己处理 N=2，但单独跑 `scripts/step2_train_variants.sh` 不会自动遵守 `--quick`。([GitHub][24])
* README 提到 “see top-level repo `requirements.txt`”，但当前 main 分支 raw `requirements.txt` 返回 404；这会影响新用户复现实验环境。([GitHub][1])

## 问题 7：通道对齐假设没有强校验

`score_channels()` 假设不同 variant 的同一 module 有相同 channel ordering 和数量。这在同一模型/同一 LoRA 配置下通常成立，但工程上最好 assert channel key 一致，否则未来扩展到不同 target modules、不同 rank 或不同 adapter 格式时可能 silent error。([GitHub][3])

# 18. 可改进之处

## 算法层

1. **从 adapter_config 自动读取 LoRA rank/alpha**
   不要手动依赖 `experiment.yaml` 的 `lora_r` / `lora_alpha`；训练产物的 `adapter_config.json` 才是 ground truth。

2. **加入 magnitude-only / alignment-only ablation**
   现在有 random-prune baseline，但还可以加：

   * only norm；
   * only alignment；
   * 不同 `lambda_`；
   * 不同 `lora_suppress_ratio` sweep。
     这样能更清楚证明 Eq. 2 设计是否必要。

3. **完成 attention head path**
   `score_attention_heads()` 和 `suppress_lora_attention_heads()` 已经写了雏形，但主流程没有接入。可以作为扩展实验：MLP channel vs attention head vs hybrid signature。([GitHub][3])

4. **真正打通 full-model purification**
   目前 full-model 相关函数和 shell 分支像是预留。若要支持 full setting，应让 Step 4 根据 config 调用 `reinitialize_full_model_neurons()`，保存 full model checkpoint，并让 Step 5 使用 `base_model_override` 评估。([GitHub][4])

## 工程层

1. **补齐环境文件**
   README 提到 `requirements.txt`，但当前 main raw URL 没找到；建议加入 `environment.yml` 或 `requirements.txt`，并 pin 关键版本：PyTorch、Transformers、PEFT、safetensors、LlamaFactory commit、Wanda commit。([GitHub][1])

2. **用 Python CLI / workflow manager 替换部分 bash glue**
   现在 bash 很实用，但路径、端口、GPU 选择、skip 条件分散在多个脚本里。可以用 Typer / Hydra / Submitit / Snakemake / Lightning Fabric 做更稳健的实验 DAG。

3. **增强 config validation**
   启动时检查：

   * adapter 路径存在；
   * data path 存在；
   * LoRA rank/alpha 一致；
   * `target_modules` 能匹配 adapter keys；
   * `setting` 是否为已完整支持的值。

4. **评测 ledger 加 run_id 和去重逻辑**
   每次评测保存 commit hash、config hash、adapter path hash、timestamp、tag、seed。summary 默认只显示每个 tag 最新一次，另提供 `--all`。

5. **泛化 evaluator**
   对生成式 backdoor，关键词 ASR 不够。可以加入：

   * regex + semantic classifier；
   * task-specific judge；
   * LLM-as-judge；
   * refusal/jailbreak/code-injection 多任务指标；
   * clean utility，例如 perplexity、MT-Bench subset、AlpacaEval-style judge。

## 实验层

1. **报告方差**
   现在 variant seed 固定，random-prune seed 默认固定。建议多 seed 重复报告 mean/std。

2. **做 τ sweep**
   `lora_suppress_ratio=0.35` 是强干预。建议 sweep 5%、10%、20%、35%、50%，观察 ASR-utility tradeoff。

3. **比较真实 CROW baseline 时控制 learning rate**
   README 特别提醒：本 repo 的 post-finetune 和 baseline 用 `finetune_lr=5e-5`，而 upstream CROW release 的 consistency training 使用 `1e-3`，20× LR 差距可能主导防御效果。这个提醒很重要，因为否则比较会混入优化强度差异，而不是 defense mechanism 差异。([GitHub][1])

# 19. 从工程评审者视角评价

## 优点

这个 repo 的科研主线是清楚的：它不是简单把模型 clean finetune 一下，而是提出了一个“synthetic antigen → paired differential → cross-variant signature → channel suppression”的完整机制。代码结构也基本遵循这个主线：`data_builder`、`residual`、`scoring`、`suppression`、`evaluate` 各司其职。README 的 pipeline 与 `run_all.sh` 实现对应较好，baseline 设置也比很多研究 repo 更认真。([GitHub][1])

## 问题

主要问题是工程成熟度还不够：环境文件缺失，full-model path 未完全打通，评测指标非常 specific，配置与训练实际参数之间存在隐式假设，部分脚本提示和实际生成文件不一致。这些问题不会否定主算法，但会影响复现、扩展和他人使用。

## 可扩展性

作为科研原型，它的可扩展性不错：你可以换 variants、换 attack task、换 target modules、换 suppression ratio、换 evaluator、接入 attention head scoring。但要成为稳健工程框架，还需要把配置校验、环境、日志、实验 tracking、full-model support 和 evaluator 泛化补齐。

## 我的总体判断

这是一个**研究想法比较集中、pipeline 设计较完整、baseline 意识较强，但工程化还有明显提升空间**的 repo。它最值得学习的地方是：如何把一个“不知道 trigger、没有 clean reference”的困难设定，转化成可操作的 paired synthetic experiment；它最需要警惕的地方是：当前实验证据高度绑定 negative sentiment + keyword ASR + LoRA setting，泛化到其他任务或 full-model defense 还需要更多工程和实验验证。
